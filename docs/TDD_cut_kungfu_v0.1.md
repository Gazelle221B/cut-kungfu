# 『カット!カンフー(仮)』技術設計書(TDD)v0.1

TDDは Technical Design Document(技術設計書)と解釈し、GDD v0.2を実装する設計として書きました。未検証の設計案で、Unity上ではまだ何も動かしていません。API名は導入する版のドキュメントで確認が要ります。

## 1. 範囲と前提

| 項目 | 内容 |
|---|---|
| 対象 | ソロの試作から縦切りまで(段階0〜3)。協力モードは拡張点のみ |
| 環境 | Unity 6系、URP、com.unity.ai.inference 最新版、GPUバックエンド |
| モデル | MotionBricks SOMA FP32(ONNX opset 17、30関節) |
| 対象外 | オンライン同期、マッハとズーム、投げなど二者間の動き |

## 2. 中心となる設計判断

スロー中に先行生成し、解除時の遅延をなくします。

カット発動時に、主人公を手付けの構えに移して静止させる。

文脈は「構えで静止した4ポーズ」に固定される。

プレイヤーがブリックを置くたびに、裏で連鎖生成を進める。スローは実時間で最大4秒あるので、推論が遅くても間に合う。

生成済みの動きを半透明のゴーストで見せる。

解除時は、生成済みの動きを再生するだけになる。

- 利点:解除から初撃までの遅延がなくなり、構えへの切替が文脈に急な速度として入る問題も消える。プレイヤーは結果を見てから欲張る量を決められる。
- 代償:発動前の勢いが技に乗らない。物足りなければ、構えを「発動時の速度を残した4フレームのクリップ」に差し替える。
- 未検証:静止した文脈から誇張した決めポーズへ、キレよく到達するか。

## 3. モジュール構成

| モジュール | 役割 | 依存 |
|---|---|---|
| MbInference | モデルの読み込み、テンソルの入出力、非同期の結果取得 | Inference Engine |
| MbCodec | ポーズと特徴量の相互変換、正規化、境界除去、端点補正 | なし(純粋なC#) |
| PoseRecorder | 表示したポーズを毎フレーム記録し、文脈4ポーズを取り出す | なし |
| CutSequencer | ブリック列から連鎖生成を計画し、再生と割り込みを管理する | 上の3つ |
| MotionMixer | 従来アニメと生成ポーズの切替、30Hzから表示レートへの補間 | Animator、Playables |
| Retargeter | SOMA骨格からゲーム用キャラへ変換する | — |
| LimbIK | 打撃の命中補正(2ボーンIK) | — |
| GameClock | スローの時間倍率を管理する | — |
| ReplayStore | NG用に関節姿勢を保存し、再生する | PoseRecorder |
| Tuning | 調整値の外部ファイル読み込みと即時反映 | — |

MbCodec と PoseRecorder をUnity非依存にしておくと、エディタ外で単体テストできます。

## 4. データ構造

```csharp
Copypublic struct MbPose {              // 1フレーム分
    public Vector3 rootPos;          // ワールド、メートル
    public float heading;            // Y軸回りの向き
    public Vector3[] jointPos;       // 29関節(ルート以外)
    public Matrix3x2[] jointRot6D;   // 30関節の6D回転
    public Vector4 footContact;      // かかと・つま先の接地(0〜1)
}

public class Brick {                 // ScriptableObject
    public MbPose[] frames;          // 4フレーム(0.1秒)
    public int tokenMin, tokenMax;   // 生成の長さ(6〜16)
    public int transitionEarly;      // 早め遷移のフレーム数
    public bool isFinisher;          // trueなら1ポーズだけ使う
    public Transform pivot;          // 小道具系のみ
}

public class Segment {               // 生成1回分の結果
    public MbPose[] frames;          // 18〜58フレーム、30Hz
    public int transitionFrame;      // ここで次のセグメントへ移る
}
```

## 5. 推論層(MbInference)

### 入出力

| 入力 | 形状 | 型 |
|---|---|---|
| global_root_values | [N,8,5] | float |
| local_root_values | [N,8,4] | float |
| local_poses | [N,8,267] | float |
| has_*(上の3つのマスク) | [N,8] | int |
| allowed_pred_num_tokens | [N,11] | int |

出力は pred_global_motions [N,64,366] と pred_num_tokens [N] です。有効なのは先頭の「4×トークン数」フレームで、両端3フレームを捨てると18〜58フレームになります。Source

### 実装方針

- Worker:起動時に1つ作り、使い回す。入力テンソルも確保したまま中身だけ書き換える。
- 結果取得:メインスレッドを止めない非同期の読み戻しを使う。前に示した同期版のコードは検証専用とする。
- ウォームアップ:ロード画面でダミー推論を1回走らせ、初回の遅さを隠す。
- キュー:要求は1本の待ち行列で順に処理する。古い要求は破棄できるようにする。
- バッチ:Nは可変なので、協力時は2人分をN=2でまとめる。
- 366次元の内訳:モデルカードと soma_n1.json から読み取って MbCodec に定義する。私はこの内訳を確認していない。

## 6. 前後処理(MbCodec)

- 推論前:最後の文脈ポーズの地面位置と向きを取り除き(高さは残す)、+X向きに揃える。目標ポーズも同じ変換にかける。
- 推論後:ワールド位置と向きを復元し、境界フレームを除去する。
- 端点補正:始点が文脈に、終点が目標に一致するよう補正する。ONNXの生出力には含まれない処理で、公式エンジン(Apache 2.0)のPython実装を移植する。Source
- 座標:SOMAはY-up・メートルでUnityと合う。左右の手系は未確認なので、段階0で鏡像にならないかを見る。

## 7. カット技の実行(CutSequencer)

### 状態遷移

| 状態 | 入る条件 | 処理 |
|---|---|---|
| 通常 | — | 従来アニメ。毎フレーム記録 |
| 構え | カット発動 | 構えへ移行して静止。GameClock を0.1倍に |
| 配置 | 構え完了 | ブリック追加ごとに先行生成。ゴースト表示 |
| 実行 | 解除 | セグメントを順に再生。到達時にヒットストップ |
| 見得 | 最後のブリック到達 | 静止ポーズを保持 |
| 中断 | 実行中の被弾 | 再生を止め、被弾アニメへ |

### 連鎖の先行生成

- 1個目:文脈は構えの4ポーズ。
- 2個目以降:前のセグメントの遷移点直前の4フレームを、文脈として先取りする。再生は決定的なので、実行前に連鎖全体を作れる。
- 破棄条件:実行中にIKや被弾で表示ポーズが計画から外れたら、後続を捨てて実際の記録から再生成する。IK補正がどの程度まで許容されるかは未検証。
- ブリックの差し替え:配置中に途中のブリックを変えたら、それ以降のセグメントを作り直す。
- 記録の規則:表示したポーズは、IK適用後の最終結果を記録します。文脈は直近0.1秒から30Hzで4つ取り出します。Source

## 8. 1フレームの処理順

1. 入力の読み取りと GameClock の更新。
2. ゲームロジック(敵AI、判定、状態遷移)。
3. 完了した推論結果の受け取り。
4. MotionMixer がポーズを決める(従来アニメか、生成セグメントの補間)。
5. Retargeter でキャラの骨に書き込む。
6. LimbIK で命中補正。
7. PoseRecorder と ReplayStore に最終ポーズを記録。
8. 描画。

4〜7は LateUpdate 以降にまとめ、Animatorの評価後に上書きします。

## 9. アニメの混合(MotionMixer)

- 従来アニメから生成へ:記録された表示ポーズが文脈になるので、ブレンドは不要。
- 生成から従来アニメへ:見得や中断の後は、短いクロスフェード(【0.1秒】)で戻す。
- 補間:30Hzのセグメントを、位置は線形、回転は球面で補間して表示レートに合わせる。
- ヒットストップ:セグメントの再生時刻を止める。GameClock とは別に持つ。
- リターゲット:最初はゲーム用キャラをSOMAと同じ骨格比率で作り、変換を骨の対応表だけで済ませる。体型の違うキャラは縦切り以降に回す。

## 10. 時間管理(GameClock)

独自の時間倍率を持ち、敵、物理、エフェクトはここから経過時間を受け取る。

UIと入力は実時間で動かす。

Time.timeScale を使わない理由:協力時やヒットストップで、対象ごとに倍率を変えたいため。

## 11. リプレイとNG(ReplayStore)

- 保存内容:全キャラの関節姿勢、小道具の位置、カメラ、発生イベントを毎フレーム。
- 方式:直近【5秒】を循環バッファで保持し、倒れた時に切り出す。
- 圧縮:回転を16ビットに量子化する。1キャラ30関節で、1秒あたり数十KB程度の見込み(概算)。
- 選別用の印:「多ブリック中の被弾」「見得の直前」「小道具との衝突」をイベントとして記録する。
- 複数キャラ対応:最初からキャラID付きで保存する。

## 12. 調整値(Tuning)

GDD 16章の値をJSONで持ち、ファイル変更を監視して実行中に反映する。

ブリックごとの値(トークン数、早め遷移)は、ブリック資産の側に置く。

デバッグ画面で、生成の所要時間、文脈4ポーズ、目標ポーズ、セグメント境界を可視化する。

## 13. 性能予算

| 項目 | 目標(仮) | 根拠・状態 |
|---|---|---|
| フレーム時間 | 16.6ms(60fps) | GDD |
| 1回の推論 | 100ms以内 | 先行生成なので緩い。未測定 |
| 4連鎖の合計 | 400ms以内 | スロー中に完了すればよい |
| 推論中のフレーム落ち | なし | 推論と描画がGPUを取り合うため、要確認 |
| VRAM(モデル分) | 実測後に決定 | FP32で757MBの重み |

参考値はRTX 4090とTensorRTで1件2.50ms、8件で2.96msです。Source Unityでの速度は別物として測ります。

## 14. 配布とビルド

- 開発中:FP32に固定する。
- 配布:Float16量子化版を同梱する(約半分のサイズ)。GPUでの出力と速度は変わらないとの報告がある。Source
- 同梱物:Apache 2.0のライセンス文と著作権表示、モデルの契約文書。サンプルモーションはビルドに含めない。
- 最低動作環境:段階0の計測後に決める。

## 15. テスト計画

| 種類 | 内容 | 合格の目安 |
|---|---|---|
| 基準比較 | 同じ入力をPython版とUnity版に流し、出力を比べる | 関節位置の差が【1cm以内】 |
| コーデック往復 | ポーズを特徴量にして戻す | 元と一致 |
| 連続性 | セグメント境界での関節速度の飛び | しきい値以内 |
| 連鎖の安定 | 50回連鎖しても姿勢が崩れない | 目視と足滑り量 |
| 量子化 | FP32版とFloat16版の出力差、VRAM使用量 | 差が基準比較と同程度 |
| 性能 | 推論時間、推論中のフレーム時間 | 13章の予算内 |
| 中断 | 実行中の任意フレームで被弾させる | 破綻なく被弾アニメへ移る |

基準比較の入力には同梱サンプルを使えますが、評価用なのでリポジトリの製品側には入れません。

## 16. 協力モードへの拡張点

CutSequencer と PoseRecorder をキャラごとのインスタンスにする。

MbInference の待ち行列は共有し、同時要求をバッチにまとめる。

GameClock は全体で1つ(共有スロー)。

## 17. 段階0の作業(1週)

1. 既製パッケージ tools.doji.motionbricks を試し、実装範囲とライセンスを確認する。
2. MbInference を作り、ダミー入力で出力の形状を確かめる。
3. MbCodec を移植し、基準比較テストを通す。
4. 棒人間で、静止した構えから目標ポーズへの生成を表示する。
5. 推論時間、推論中のフレーム時間、VRAMを測る。
6. 誇張した決めポーズを数種類試し、到達のキレを目視する。

6の結果が悪ければ、2章の設計を見直します。

## 18. 未決事項

- 生成の決定性:同じ入力で毎回同じ動きが出るかは未確認。先行生成とゴースト表示は影響を受けないが、テストの作り方が変わる。
- 既製パッケージの採否:品質とライセンス次第。
- GPUの取り合い:推論が描画を止める場合は、推論を数フレームに分割できるか調べる。
- IKと文脈のずれ:補正が大きいと、先行生成を捨てる頻度が上がる。
- 静止文脈の影響:勢いのない出だしで、技が鈍く見える可能性がある。
